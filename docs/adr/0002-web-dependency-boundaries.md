# 0002：Web 前端单向依赖边界

## 状态

已接受

## 背景与目标

Web 项目包含页面、组件、Pinia store、API 客户端、缓存和计算逻辑。若页面直接调用 API、基础设施反向读取 store，或业务流程分散在多个组件中，调用链会变得隐蔽，增加人工与 AI 修改代码时的集成和排错成本。

本决策建立可检查的单向依赖边界，使一个功能的入口、流程协调、领域计算和基础设施职责清晰。它降低故障定位范围，但不承诺消除所有缺陷。

## 范围与非目标

本决策适用于 `src/` 下新增或修改的 Web 代码。

不要求一次性重构所有既有模块；不规定文件行数；不禁止合理的共享函数复用；不替代 OpenSpec 对用户可见行为的规格管理和测试验证。

## 决策

前端采用以下逻辑层。目录可随业务演进调整，但职责和依赖方向保持不变。

| 逻辑层     | 当前主要位置                          | 职责                                               |
| ---------- | ------------------------------------- | -------------------------------------------------- |
| 展示层     | `views/`、`components/`               | 路由页面、渲染、交互事件和展示状态                 |
| 应用协调层 | `stores/`，必要时按业务域新增应用服务 | 请求编排、加载状态、错误处理、状态变更和跨模块流程 |
| 领域逻辑层 | 按业务域建立的纯计算模块              | 指标计算、筛选、策略判断和数据转换                 |
| 基础设施层 | `api/`、缓存、导出和浏览器能力封装    | HTTP、持久化、文件下载和运行时能力                 |

允许的依赖方向如下：

```text
展示层 -> 应用协调层 -> 领域逻辑层
                     -> 基础设施层
```

展示层可使用展示专用的格式化函数和子组件。应用协调层可组合领域逻辑与基础设施层。领域逻辑层保持纯粹，不读取或修改框架和外部运行时状态。基础设施层只提供技术能力，不导入上层模块。

## 禁止关系

- `views/` 或 `components/` 直接调用 `api/`。
- `api/`、缓存、导出或其他基础设施模块导入 `stores/`、`views/` 或 `components/`。
- 领域逻辑导入 Vue、Pinia、axios、浏览器 DOM 或全局 store。
- 通过相互导入形成循环依赖。
- 在组件或页面中编排跨业务域流程。

## 实施与迁移

新功能从需求开始按此边界实现。既有代码采用“触及即迁移”：当一个任务修改某条调用链时，将该调用链中可以无行为变化迁移的职责归位，不为遵守本决策进行无关的大规模重构。

详情页等直接请求 API 的既有路径，应优先迁移为“页面调用对应 store 或应用服务，协调层调用 API”。涉及行情、收益率、筛选或策略判断的重复逻辑，应优先抽取为按业务域命名的纯函数，并以输入输出示例验证。

## 验证方式

- 代码评审检查新增和修改的 import 是否符合本决策。
- 领域纯函数必须覆盖正常值、边界值和异常输入的自动化验证。
- 修改用户可见行为时，按 OpenSpec 流程更新规格并运行对应验证；仅做无行为变化的职责迁移时，至少运行构建及受影响页面或逻辑的回归验证。
- 引入自动化 import 边界检查前，以上规则由任务实现者和评审者共同执行；边界稳定后再将其加入 CI。

## 后果与风险

流程会更集中、更容易观察，但过度将逻辑堆入单一 store 会形成新的复杂中心。因此 store 和应用服务应按 `convertible`、`lof`、`hkipo` 等业务域拆分，并保持公开操作的输入、输出和错误语义清晰。

严格禁止所有模块复用会导致重复代码，故本决策只限制不合理的反向依赖和循环依赖，不限制同层的明确共享依赖。
