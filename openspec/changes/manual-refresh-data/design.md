# 设计

## 上下文

共享布局已经展示全局 `lastUpdated`，业务页面也各自拥有 `loadAll` 或详情加载函数。服务端除综合市场概览外已支持 `refresh=true`，但布局不能直接依赖业务 API；页面需要把当前路由的业务刷新动作注册到应用 store。

## 目标与非目标

**目标：**

- 用一个稳定的顶部入口刷新当前路由数据。
- 复用各页面已有的加载编排和 loading 状态。
- 手动刷新时真正请求服务端强制读取。
- 桌面端和移动端都保留可访问的图标按钮及加载态。

**非目标：**

- 不做定时自动刷新。
- 不改变缓存 TTL、上游采集策略或数据模型。
- 不把服务端响应时间误称为上游事实时间，也不保证强制刷新一定带来新数据。

## 决策

### 使用应用 store 注册当前页面刷新动作

`app` store 保存当前路由的刷新回调、注册键和刷新状态。页面在挂载时注册自己的 `loadAll` 或详情加载函数，在卸载时按键清理；布局只调用 `appStore.refreshCurrentPage()`，因此不直接依赖业务 store 或 API。

备选方案是布局按路由导入所有业务 store。该方案会让展示组件承担跨业务编排并扩大依赖边界，故不采用。

### 通过现有 API 参数传递强制刷新

各 API 方法增加可选参数并将 `refresh=true` 放入查询参数；store 的初始加载沿用默认参数，手动刷新传入 `refresh: true`。服务端首页综合概览对其四个组成数据统一传递强制刷新。

备选方案是给每个页面增加独立按钮并复制刷新逻辑。它会造成入口不一致，且详情页容易遗漏，故不采用。

### 成功后更新共享更新时间

共享 store 只在刷新回调成功完成后写入 `lastUpdated`；失败时不覆盖已有时间。这个时间表示本次页面数据读取完成时间，数据是否来自缓存仍由服务端元数据决定。

## 风险与取舍

- [风险] 强制回源可能比普通读取慢，且多个组成请求会增加上游压力 → 仅响应用户主动操作，按钮加载期间禁止重复点击，并复用服务端限流。
- [风险] 某些已有 store 会把子请求错误降级为局部成功 → 保留页面既有降级语义，不伪造空数据；按钮只反映页面刷新编排是否结束。
- [风险] 页面切换时旧页面异步卸载可能清理新页面回调 → 注册和清理都使用路由键，清理前核对当前注册键。

## 迁移计划

先部署服务端综合概览的 `refresh=true` 支持，再部署 Web；旧 Web 不传该参数时服务行为保持不变。若需回滚，先回滚 Web 按钮和参数，再回滚服务端路由改动。
